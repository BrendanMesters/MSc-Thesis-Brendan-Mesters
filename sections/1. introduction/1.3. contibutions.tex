\noindent \textbf{1. A Signal Processing Method for Sparse Point Cloud Interpretation}\\
Our first contribution is a framework for the cleaning, enhancing and interpretation of sparse mmWave radar point clouds.\\
This framework comprises:
\begin{itemize}
    \item 
        A \textit{spatio-temporal filter} for pointclouds, which uses the local density and the prior frames to filter out both \textit{dense single-frame noise spikes}, as well as more \textit{consistent low-density noise}.
    \ednote{split het volgende bulletpoint tot been few-shot online learning \textbf{EN} de data enhancement}
    \item 
        A \textit{data enhancement} technique to prioritise the points produced by the user's hands.
        This is achieved through a \textit{few-shot online learning} step, which gathers context data of the scene, also providing valuable information about the user's position and arm span.
    \item 
        A \textit{stabilising angle estimation} method, which uses the context gathered by the data enhancement system to estimate which discrete arm angle range the user's arms are in.
        Stabilisation methods are employed to counteract jitter and noise spikes.
\end{itemize}


\noindent \textbf{2. A Real-Time Software Architecture: 'IAmMuse'}\\
Our second contribution is a multi-threaded full pipeline implementation of this methodology, called 'IAmMuse'.
It is designed with robustness and fast response times in mind, to be able to run on more resource-constrained hardware.\\
For this contribution, we present:
\begin{itemize}
    \item 
        A custom high-performance driver for the radar communication protocol, implemented in Rust.
        This development yields a platform-agnostic solution, resolving the compatibility limitations of the vendor-supplied driver while providing a native, low-latency interface, enabling seamless integration into the rest of the pipeline.
    \item 
        A fully asynchronous and multi-threaded implementation of the pipeline shown in \cref{figure: system state diagram}.
        This architecture ensures that data processing can start as soon as a data packet arrives from the mmWave radar.
        This enables optimal hardware utilisation, even on more resource-constrained hardware.
    \item 
        A custom visualizer in Python, providing a direct view into the system's internal state.
        This is an essential tool, allowing us to tune and monitor the system through visual verification of many of the pipeline steps.
\end{itemize}


\noindent \textbf{3. A Comparative Evaluation Against the State of the Art}\\
Our third contribution is a quantitative comparison with an SoA HPE interpretation system.
For this, we compared IAmMuse to the DL model MARS~\cite{an2021mars}, to assess the efficacy of the IAmMuse framework.\\
The findings from this benchmark are that:
\begin{itemize}
    \item 
        IAmMuse outperformed the best-performing MARS model by a factor of 1.5 for correct state predictions, on our evaluation data set.
        The output of MARS was often unstable, rapidly switching between different predictions.
    % \ednote{Turn it around, "if we give it poor data" THEN "we get poor output"}
    \item 
        If MARS is trained using the data from the online few-shot training, then the performance is only slightly better than random guessing.
        % MARS' results are only slightly better than random performance when it is trained using the same data IAmMuse uses for its online few-shot training.
        % MARS performs only slightly above a chance-level performance when it is trained in the same data IAmMuse uses for its online few-shot training.
        In this scenario, IAmMuse had an accuracy 4 times higher than MARS.
    % \ednote{Misschien anders vertellen:\\ Je moet MARS met echt dezelfde data trained als je gebruiks data, also dit niet goed genoeg match dan krijgt hij been enorme bias.}
    \item 
        The training data for MARS also had to match the evaluation data very closely; using a different mmWave HPE dataset, for example, produced a model that was very prone to bias.
        These models predicted the same state, regardless of the input data, more then 90\% of the time.
        % The MARS model was prone to severe bias, predicting the same output state more than 90\% of the time.
        % Careful training set selection was required to mitigate this behaviour.
\end{itemize}
