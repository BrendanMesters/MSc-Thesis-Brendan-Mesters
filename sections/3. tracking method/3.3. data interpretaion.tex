\subsection{Angle Estimation}
\label{sub-section: tracking method - data interpretation - angle estimation}

We want to predict a specific zone, \textit{low}, \textit{middle}, or \textit{high}, for each hand.
These zones are represented to be the volume within a \textit{wedge} of the ball, as visualised in \cref{figure: internal data view - b}. 
Note that there are two regions (at the top and bottom) that are not a part of any zone.
An alternative method defines these zones as angle ranges within the camera's projection plane. 
Here, the points are classified based on the angle of the vector extending from the projected sternum to the point in question.
This produces an identical result, except for the fact that points which fall outside the ball can still be categorised into one of the position zones.
% Another equivalent way to specify a particular zone is as an angle range in the projection plane of the camera.
% Here, a point gets assigned to a certain angle range, dependent on the angle of the vector going from the user's sternum to that point in that given projection.
% Each point can be assigned to a zone, using these angle ranges, and the angle of the vector going from the encompassing ball's centre to the specific point.

The point cloud is now divided into points contained within the six position zones and points not contained in any position zone.
We now assign a weight to each position zone, based on the weight of all the points contained in that specific zone.
The weight of each position zone can be seen as the prediction likelihood of the user's arm actually being in that specific zone.
Lastly, we find the right-hand position zone with the highest weight, and the left-hand position zone with the highest weight; these are now our zone predictions.

\subsection{Output Stabilisation}
\label{sub-section: tracking method - data interpretation - stabilisation}
% \ednote{STATE VS ZONE< MAKE SURE YOU HAVE IT CORRECT}

% \ednote{intro: There are still some issues, however.}
This estimation system still has some issues, in particular when it comes to stability.
The first issue we consider is that of the data sparsity and occasional intermittency observed in the mmWave radar.
This lack of data results in some frames where a significant portion of the position zones has a low weight and, thus, a low certainty.
These low certainties can lead to unsubstantiated, near-random predictions.
To counteract this, we enforce a weight threshold that a zone must attain before we consider the prediction to be \textit{valid}.
If a frame does not contain any valid position zone predictions for the left or the right hand, then the previous prediction for that zone is used to avoid unsupported predictions.


% \ednote{mmWave Sparsity:\\ Occasional \textit{low certainty} predictions lead to unreliable predictions.\\ MITIGATION: Minimal zone weight to be considered a \textit{valid zone}\\ If no valid zone is found, we default to the previous prediction.\\ CONSIDERATION: We will be ignoring some frames; this data could be added to the next frame, but we don't do this as we consider the data stale.}

% \ednote{Noise spikes:\\ Most of the currently existing stuff is good, though I do need to change some wording.\\ Specify the delay in \textit{frames} not in \textit{millis}.}
A further challenge we have to solve is that of noise spikes, which throw off the predictions.
% The second issue we have to solve is noise spikes, which throw off the prediction.
Noise spikes are still at times permitted by the filter, for example, when two noise spikes happen in quick succession in the same region.
These spikes can significantly influence the position zone weights, thus affecting the predicted zone.
This manifests itself as incidental \textit{random predictions}, which should be mitigated.
We do this by introducing a temporal consistency constraint, since \textit{valid predictions} are assumed to remain stable across frames.
This constraint is enforced by only switching our output state if the same state has been predicted twice.

% Lastly, if the user holds their arm at the boundary between two position zones, then the random sampling of the mmWave radar will result in our system randomly predicting either zone.
This is an incorrect behaviour as the user provides the same input (a stationary arm) and receives a different input on consecutive frames.
This issue only occurs at the boundary between two position zones, and is caused by that boundary's specific position.
Our mitigation strategy moves the boundary between the zones in such a way that points near or at that boundary are assigned to the currently selected zone, through a hysteresis mechanism, see \cref{figure: active zone increase}.
With these mitigation strategies in place, the output of the prediction system is sufficiently stabilised.
